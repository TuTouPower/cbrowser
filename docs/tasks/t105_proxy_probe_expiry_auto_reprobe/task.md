# Task spec

## 背景

用户 2026-11-23 反馈代理列表「重启后测速结果没了」。现场核实：结果并未因重启从 SQLite 丢失——`cbrowser-db` 命名卷中 88 个代理的最新观测为 84 条 `ok`（其中 77 条已过 24h TTL）+ 4 条无 TTL 的 `failed`；生产 `ProfileRepository` 受控时间复现显示同一行在 TTL 前返回 `ok, 619ms`，TTL 后被 `_visible_observation` 隐藏、回落 `unknown` → UI「未测速」，而 `failed` 行始终可见，与截图逐行吻合。`docs/specs/proxy_management.md:54` 明确要求「观测过期时旧观测立即失效……并自动重新探测」，但代码只在创建/端点变更时 `_schedule_probe`，启动仅 `resume_pending_probe_jobs()`，过期后无任何重测入口，代理长期停在「未测速」。用户裁决：保留 24h TTL，按 spec 补服务端自动重测。

## 契约区

### 范围

- `ok` 观测过期的检测与自动重测触发：API 启动恢复 + 有界周期巡检（周期可配置、可注入时钟，默认 ≤ 5 分钟）。
- 自动重测复用现有服务端作业编排、探测 runner 与 `CBROWSER_PROBE_JOB_CONCURRENCY` 配额；过期集合去重、在途去重、失败不无限重试。
- 所有消费观测的读路径（列表状态列/卡片/编辑弹窗/会话详情、国家与城市筛选范围）随重测结果恢复，不新增前端本地测速状态。
- 后端单元与集成测试、前端回归测试，以及 spec / blueprint 文档同步。

### 非范围

- 不改 `OBSERVATION_TTL_SECONDS = 24h` 的数值，不把「测速延迟」从 Geo 观测 TTL 解耦（用户已裁决）。
- 不改 `failed` 观测无过期时间、永久可见的语义（p168 已单列的未确认残余）。
- 不改手动单条/批量测速入口与 t094/t095 的 SSE 进度语义。
- 不新增调度状态表或数据库迁移：过期集合优先从观测表派生。
- 不处理多 API 实例并发巡检（单机单人部署，见有意不测）。

### 验收标准

只写可观察、可独立验证的行为；每条使用稳定且不复用的 `AC-NNN`。需真实部署或人工环境验证时在编号前加 `[deploy]`。创建时均为未勾选（`- [ ]`）；实施验证通过后由实施 Agent 就地打勾（`- [x]`）；由 Review Agent 独立复核打勾真实性。技术选型不作为行为 AC。review 判 FAIL 且需修改交付内容时，实施 Agent 撤回全部打勾，修复并重验后重新打勾；reviewer 用 `TICK-VALID` / `TICK-VOID` 逐条判定。

<!-- /规范 -->

- [ ] AC-001：代理最新 `ok` 观测超过 24h TTL 且端点指纹与凭据版本仍匹配当前端点时，服务端在下一个巡检周期（默认 ≤ 5 分钟，可配置且可用注入时钟验证）内自动发起一次探测，无需用户操作；该代理列表状态由「未测速」恢复为 `ok` 的延迟毫秒数，或探测失败时显示对应脱敏错误码。
- [ ] AC-002：API 进程启动时对已过期 `ok` 观测的代理执行与 AC-001 相同的自动重测恢复；恢复不依赖上一进程内存中的待办集合，仅从持久化观测派生。
- [ ] AC-003：自动重测与手动测速共用同一服务端作业编排与 `CBROWSER_PROBE_JOB_CONCURRENCY` 配额；N 个代理同时到期时，在途探测并发不超过配额，超限代理排队并依次完成，不出现瞬时 N 路并发。
- [ ] AC-004：自动重测去重与收敛：同一代理在已有 `pending` 观测或在途作业时不得重复提交；自动重测失败落 `failed` 观测后，在该 TTL 周期内不再自动重试，用户手动单条或批量测速仍可覆盖该结果。
- [ ] AC-005：自动重测成功后，`GET /api/v1/proxies/collection` 中该代理的 `latency_ms` / `country_code` / `country_name` / `city` / `observation_status` 恢复为有效值，`GET /api/v1/proxies/countries` 的国家与城市范围同步包含该代理；前端列表状态列、卡片视图、编辑弹窗、会话详情均展示恢复后的观测，不依赖前端本地测速缓存。
- [ ] AC-006：端点或凭据变更触发的既有自动探测（t052 AC-006）仍恰好执行一次并正确收敛，不被新巡检重复触发、覆盖为 `pending` 或回滚到过期状态。

### 有意不测

- 多 API 实例并发巡检：单机单人部署只有一个 API 写者，多实例重复巡检不在本 task 边界。
- 真实公网代理出口可达性：探测准确性由 t094/t096 的单元与真实 Docker E2E 覆盖；本 task 只验证过期触发与结果恢复，不重复验证代理网络。

### 测试策略

- 后端单元：注入时钟跨越 TTL，断言巡检与启动恢复提交探测、pending/在途去重、失败不重试、并发峰值受配额约束。
- 集成：`GET /api/v1/proxies/collection` 与 `/countries` 在过期前后及重测完成后的结果一致性；作业终态仍以作业读模型为准。
- 前端：SSE `probe_job_progress` 与观测失效重取驱动行状态从「未测速」恢复；卡片/编辑弹窗/会话详情消费同一服务端观测；刷新重挂无本地测速状态。
- 证据补强：用 `.scratch/repro_probe_result_after_restart/cbrowser.db` 快照在冻结时间下重跑，验证修复后同一行不再回落 `unknown`（作业完成后）。

### 风险与回退

- 风险：大量代理同时到期造成探测峰值与 SQLite 写放大；巡检与手动作业/端点变更探测重复；失败代理被反复重测。
- 回退：关闭周期巡检（配置开关）即回到仅手动测速语义；或移除巡检调度，保留既有 pending→ok 观测与作业路径。无数据迁移或 schema 需回滚。

### 依赖与约束

- 复用 t094/t095 的作业编排、runner 注入与并发配额；探测凭证只从服务端已存端点装载（t052 AC-009）。
- 巡检周期与时钟必须可配置/可注入，不 patch 标准库 time 模块；不得为调度新增数据库表或迁移。
